# Repository Guidelines

## Project Structure & Module Organization

- `app/` contains App Router segments, route layouts, metadata routes (`sitemap`, `robots`), and server components. Colocate page-level assets within each segment.
- `components/` stores reusable HeroUI-driven widgets. Split complex pieces into subfolders with an `index.ts` barrel when exports exceed two items.
- `config/` and `data/` hold runtime configuration and static content. Update them instead of hardcoding strings in JSX.
- `styles/` defines the Tailwind entry point and global CSS; `public/` serves static media (profile image, résumé, favicon). `public/pdf.worker.mjs` is generated by `prebuild` and is gitignored.
- `scripts/` contains build-time helpers that run under Bun.
- There is no `lib/` or `types/` directory. Colocate a type with the module that owns it and re-export it only when it is shared.

## Build, Test, and Development Commands

- `bun install` installs dependencies and updates `bun.lock`.
- `bun run dev` copies the PDF.js worker and starts the Next.js dev server.
- `bun run build` performs a production build and prerender; run before publishing changes.
- `bun run start` serves the optimized build locally.
- `bun run lint` reports ESLint findings without changing files; `bun run lint:fix` applies safe fixes.
- `bun run format` writes Prettier formatting; `bun run format:check` verifies it in CI.
- `bun run typecheck` generates Next.js route types and runs `tsc --noEmit`.
- `bun run check` runs lint, formatting, and type checks together.

## Coding Style & Naming Conventions

- TypeScript is strict; annotate props with dedicated interfaces/types and avoid `any`.
- Imports are grouped by type → builtin/node → external → `@/` aliases → relative paths.
- Use arrow functions for components, add `"use client"` only when stateful/browser APIs are needed, and keep callbacks as the last JSX props.
- Styling relies on Tailwind utility classes, `clsx`, and `tailwind-variants`; consolidate conditional logic in helper functions when it spans multiple props.
- Maintain 2-space indentation, LF line endings, and Prettier defaults. Use camelCase for variables and PascalCase for components, files, and directories that export React elements.
- The background animation is intentionally always on; the canvas pauses only while the tab is hidden. Do not add `prefers-reduced-motion` gating without confirming that product decision.
- The app bar uses a small `requestAnimationFrame` scroll helper in `components/navbar.tsx` rather than native `scrollIntoView`, because native smooth scrolling is disabled by some OS motion settings. The glide deliberately runs even when the OS asks for reduced motion; wheel, touch, or key input cancels it instead. Keep the 3rem navbar offset (`NAVBAR_OFFSET` and `scroll-margin-top`) in sync if the header height changes.

## Testing Guidelines

- No automated test runner ships yet; pair linting, formatting, and type checks with manual UI verification covering new states and breakpoints.
- When adding tests, colocate them beside the implementation (`*.test.tsx`) and document the command required to run the suite in this guide.
- Launch browsers for UI checks with extensions disabled and a throwaway home, because the sandbox mounts `~` read-only and KDE's system-wide Plasma Integration extension otherwise spams `~/.config/plasma-browser-integration-hostrc not writable` on every launch:
  `HOME=$PWD/.tmp-browser XDG_CONFIG_HOME=$PWD/.tmp-browser/.config chromium --headless=new --no-sandbox --disable-gpu --disable-extensions --user-data-dir=$PWD/.tmp-browser/profile --screenshot=$PWD/.tmp-browser/shot.png --window-size=1440,900 <url>`
- Keep browser profiles, screenshots, and other run artifacts under `.tmp-*` so they stay gitignored, and delete them when done.

## Commit & Pull Request Guidelines

- Follow Conventional Commit prefixes observed in history (`feat:`, `refactor:`, `fix:`, `chore:`, etc.) and write concise imperatives under 60 characters.
- Keep commits scoped to one change-set and include context in the body when behaviour shifts or data files update.
- Pull requests should summarise the impact, link relevant issues, list manual test steps, and attach UI screenshots or recordings when the layout changes.
